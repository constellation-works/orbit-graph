## Q5 — Unresolved impact: false associations and missed real callers

**Every false association found by manual inspection.**

1. 645 of the 650 entry points and 288 of the 288 `call_path` candidate tests carry a
   `heuristic_match` edge. Spot-checking the largest group: every `.execute(&runtime)`
   call site in `crates/orbit-cli/src/command/**/tests/` is attached by bare name, the
   same mechanism study 2 traces to **ORB-12416**.
2. 133 of the 136 `import_relationship` candidate tests for `TaskComplexity:enum` are
   test files that import *something* from `orbit_types::task` or `orbit_core` and do
   not test complexity handling at all. Real module edges, correctly labelled
   file-level, substantively unrelated.
3. Ten of the twelve `uncertain` rows are symbols the source proves unchanged (Q1).

**Every missed real caller found by manual inspection.**

1. **Every cross-crate reference to `TaskComplexity`.** The head index stores
   4 refs at `exact` (all inside `crates/orbit-types/src/task/model.rs`) and 56 refs
   at `fuzzy_name` with `target_qualified = NULL`, spread over 32 files in
   `orbit-cli`, `orbit-config`, `orbit-core`, `orbit-store`, `orbit-web` and
   `orbit-types`. The import rows that would resolve them exist — for example
   `('crates/orbit-config/src/crew_pools.rs', 'orbit_types::task', 'TaskComplexity')` —
   but the resolver refuses because four indexed symbols share the name
   `TaskComplexity`: the enum plus `<TaskComplexity as Display>`,
   `<TaskComplexity as FromStr>` and `<TaskComplexity>`. Filed as **ORB-12417**, with
   a two-crate before/after reproduction showing that adding two ordinary `impl`
   blocks is enough to erase every cross-file reference from `refs`.
   Named consumers that should have appeared and did not:
   `crates/orbit-web/src/api/tasks.rs:142, 264, 601@156dc93d940e`,
   `crates/orbit-cli/src/command/task/update.rs`,
   `crates/orbit-cli/src/command/task/add.rs`,
   `crates/orbit-core/src/application/task/params.rs`,
   `crates/orbit-store/src/contracts/params.rs`, and 27 more.
2. `symbol:crates/orbit-core/src/adapter/tool_host/task_tools.rs#update:function`
   is the tool-host surface the change hardens; its inbound evidence is 200
   node-cap-truncated paths in which the resolved portion is the same fuzzy
   `execute`/`update` name fan-out.
3. 12 of the 26 queries returned zero paths at every depth, always with the three
   disclosed reasons. Sampling: the six Markdown headings in
   `plugin/skills/orbit/references/task-authoring.md` and
   `crates/orbit-core/assets/skills/orbit/references/task-authoring.md` (no callers by

**Out of scope.** Zero out-of-scope changed files; ten tree entries excluded per
snapshot at materialization, named in every `no_path_reasons` list.

**The zero entry-point figures are failures, not findings.** At depth 10 the
entry-point traversal reaches a symbol whose derived `command:` selector resolves to
a handler in another file, and the whole request returns HTTP 400:

```
resolve command selector for the head snapshot: read source span for graph show:
invalid span 4537..8073 for crates/orbit-cli/src/command/task/command.rs with 5279 bytes
```

That is ORB-12410 again, now triggered by depth rather than by the changed file. Ten
of the thirteen changed rows are this failure; only `parse_task_complexity`,
`task_tools.rs#update` and `model.rs#label:method` changed for an honest reason.

Raising the bounds does not recover any missing cross-crate reference: at

node-cap truncated, still 4896 `heuristic_match` / 60 `observed_reference` /
44 `import_relationship`, and still no resolved cross-crate consumer.

## Scripted baseline versus the service — **agent-only, not a human usability study**

| Arm | Command | Wall clock | What it answered |
| --- | --- | --- | --- |
| Baseline | `scripts/baseline.sh 3` | **205.93 s** | 5 declaration names from the diff, `git grep -w` counts, `orbit-graph sync --full` on a detached head worktree, then `refs`/`impact` per resolvable selector |
| Service, cold | `scripts/service-study.sh 3` | **466.83 s** (395.18 s to index both sides, 71.65 s question pass) | 26 changed symbols, 26 × 3 evidence depths, 26 entry-point reports, 26 candidate-test reports, 22 searches |
| Service, warm | `scripts/service-study.sh 3 --warm` | **72.94 s** (1.02 s to ready, 71.92 s question pass) | same |

The baseline recovered five names — the diff is mostly doc comments and call-site
edits, which carry no declaration header — against the explorer's 26 rows. But on
the one question this study is about, "who uses `TaskComplexity`", the baseline's
`git grep -w TaskComplexity` is *more* accurate than the explorer's resolved
evidence: it lists all 44 files, while the resolver resolves references from only
one. Agent commands, not human effort.

This study's subject is also where the explorer's per-query latency is worst. On a
warm cache, `symbol:crates/orbit-types/src/task/model.rs#TaskComplexity:enum` costs
1 141 ms p50 on `/api/evidence` at depth 3, 1 065 ms p50 on `/api/entry-points` and
1 474 ms p50 on `/api/candidate-tests` — over the one-second target at the median,
not just the tail, for the same reason the answers are wrong: the 200-node budget is
filled with `fuzzy_name` matches that still have to be walked and serialized. Full
numbers in [`performance.md`](performance.md).
