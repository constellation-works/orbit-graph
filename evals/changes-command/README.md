# Changes command: studies 2 and 3 re-run

ORB-13256 re-runs two change-explorer studies through the agent surfaces:

- [study 2](../change-explorer/2-orbit-5a5b45fec9a8.md): `orbit workspace
  teardown`;
- [study 3](../change-explorer/3-orbit-156dc93d940e.md): the `TaskComplexity`
  library type;
- surfaces: `orbit-graph changes <base>..<head>` and the
  `orbit.graph.changes` plugin tool.

It compares what the command reports with the findings the explorer
evaluation recorded, including its 2026-09-13 re-run at `EXTRACTOR_VERSION` 8.
For each study it lists what **matches**, what is **new** and what is
**missing**, and why.

**No accuracy percentage, by design**, for the reason the
[explorer evaluation](../change-explorer/README.md) gives: one number would
average a verified call path together with a name-only match to an unrelated
method. The lists below are the result.

## Setup

| Field | Value |
| --- | --- |
| Corpus | `orbit`, `git clone --no-hardlinks file://~/workspace/constellation/codebases/orbit` into a scratch directory (5125 commits); nothing was written to the sibling checkout, and the script fails if either surface writes into the clone |
| Binary | `target/release/orbit-graph` built from this change, `EXTRACTOR_VERSION` 8 |
| Host | `dk-server-1`, 15 cores, 26 GiB, shared with other agents (load average 1–10 during the runs) |
| Script | [`scripts/run-study.sh`](scripts/run-study.sh) `2` and `3` |

Committed outputs:

| File | What it is |
| --- | --- |
| `<n>-plugin.json` | The plugin response at plugin defaults, exactly as an agent receives it (pretty-printed; the compact `result` is under the 512 KiB ceiling). |
| `<n>-cli.summary.json` | A projection of the CLI document at CLI defaults (`same_module` floor). Per changed symbol it keeps status, pairing, and every kept caller, entry point and test with source, confidence and first reference. |
| `<n>-cli-fuzzy.summary.json` | The same projection with `--confidence fuzzy --max-callers 100 --max-tests 100 --max-entry-points 50`, the profile closest to the explorer's. |
| [`timings.tsv`](timings.tsv) | The wall clock of every call. |

The full CLI documents are 1–6 MB and are regenerated by the script.

## Latency

Every call returned `complete: true`. The cold calls start from an empty
cache, and each warm call repeats the same comparison immediately afterwards.

| Study | Surface | Cold | Warm | Indexing (cold) | Analysis (cold / warm) |
| --- | --- | --- | --- | --- | --- |
| 2 | CLI, defaults | 25.3 s | 18.7 s | 7.2 s | 18.1 s / 18.7 s |
| 2 | plugin, defaults | 25.9 s | 20.9 s | 6.8 s | 19.0 s / 20.8 s |
| 3 | CLI, defaults | 42.6 s | 35.4 s | 7.5 s | 35.0 s / 35.3 s |
| 3 | plugin, defaults | 42.4 s | 39.8 s | 6.0 s | 36.3 s / 39.7 s |

With `--confidence fuzzy` and the raised caps, warm runs took 10.7 s (study 2)
and 21.6 s (study 3). This run asks more and is faster: at the `same_module`
floor the library also looks for unknown-receiver calls to show at
`fuzzy_name`, which appears to cost more than admitting them outright. This is
observed, not diagnosed. An earlier run of the same binary under heavier host
load took up to 54 s cold. All numbers are well inside the plugin's 90 s
default budget, and none was cut by it.

**Cold indexing matched the ~12 s estimate; the rest did not.** Both
snapshots of a 2 200-file Rust workspace indexed in 6–7.5 s, and a warm call
skipped indexing entirely (`prepare_ms` < 0.2 s). But analysis, 25–26 changed
symbols with a bounded traversal per side, took 18–40 s and dominates both
cold and warm calls. Profiling during this task found and fixed two per-symbol
costs:

- test-file imports were re-read for every symbol;
- `runtime_invocations()` (~3 s per snapshot on Orbit) was re-read for every
  symbol.

What remains is a ~150 ms floor per traversal inside `orbit_graph`'s impact
query. See [decision D1](../../docs/design/changes-command/4_decisions.md#d1-cost-analysis-not-indexing-dominates-every-call-is-budgeted)
and its follow-up.

## Study 2

Range `1ca6416e0ba2` → `5a5b45fec9a8`, the `orbit workspace teardown` handler.

**Matches**

- **Changed symbols.** 25 rows, the same split the explorer reported: 15
  `added`, 9 `modified`, 1 `signature_changed`
  (`tests/teardown.rs#register:function`). Pairing is `same_selector` for 24
  rows and `signature_changed` for 1. The three
  `docs/runbooks/health-checks.md` headings have no callers or tests, as
  before.
- **Strongest path for `resolve_teardown_target`.**
  `teardown.rs#execute:method` → `resolve_teardown_target`, at
  `crates/orbit-cli/src/command/workspace/teardown.rs:29@5a5b45fe`, labelled
  `call_path` / `exact`, distance 1. It is the first caller listed.
- **The 12 resolved candidate tests.** All are labelled `call_path` / `exact`
  or `import_resolved`, at both the default and the fuzzy profile:
  - `teardown_plan_names_workspace_checkout_and_partition` for
    `format_teardown_plan` and `partition_bundle_count`;
  - the same five tests for `register` and for `teardown`.
- **The fuzzy `execute` fan-out is still there, and is labelled.**
  `teardown.rs#execute` has 94 callers and 115 candidate tests. At the
  default profile its 10 kept tests are all `call_path` / `fuzzy_name`, and
  the six new production functions without a resolved test reach tests only
  through `fuzzy_name` hops:
  - `resolve_teardown_target`
  - `unknown_teardown_selector`
  - `workspace_id_for_selector`
  - `refuse_if_cwd_belongs_to_another_checkout`
  - `planned_task_store_partitions`
  - `execute`

  This is the finding the explorer recorded. The difference is that every
  such item now says `fuzzy_name` next to it, and the caps put it after every
  stronger item.
- **`WorkspaceSubcommand:enum`.** 75 import-relationship candidate tests
  (`file_import`), none of them about teardown. It is the same real but
  unrelated module-edge set as before, labelled file-level.

**New**

- **A third resolved test.** `format_deleted_partition:function` ←
  `partition_summary_names_the_workspace_it_belonged_to`, labelled
  `call_path` / `import_resolved`. Verified: the test calls
  `format_deleted_partition(path, "constellation")` at
  `crates/orbit-cli/src/command/workspace/tests/teardown.rs:231@5a5b45fe`, and
  imports it at line 25. The explorer counted two of the eight new production
  functions with a resolved test; there are three.
- **A new source of candidate tests, `runtime_invocation`.** Eight tests that
  start the `orbit` binary are attached to the changed tests and helpers by
  program name, labelled `name_only`. The source did not exist when the
  explorer studies ran. The label says what it is: an association by program
  name, not a call.
- **Changed tests are their own entry points.** Each changed test is its own
  distance-0 entry point, labelled `changed_symbol` / `exact` rather than
  presented as a call path.

**Missing, or different**

- **The single dispatch site of the changed handler cites the wrong line.**
  At the fuzzy profile, `command.rs#execute:method` (the dispatcher) is
  reported as a caller of `teardown.rs#execute`, as the explorer re-run found.
  But the cited reference is
  `crates/orbit-cli/src/command/workspace/command.rs:55@5a5b45fe`, the
  `List(args) => args.execute(runtime)` arm, not line 61, the `Teardown` arm.
  All seven arms fuzzy-match every `execute`, and the evidence keeps one
  reference per caller and target. The caller is right and the cited line is
  a different arm. At the default profile the dispatcher is found (94 callers)
  but not among the 10 kept, because `fuzzy_name` sorts last. Recorded as a
  follow-up in [D11](../../docs/design/changes-command/4_decisions.md#d11-follow-ups).
- **`cli_command_handler` entry points: none**, as before. No entry point in
  either study was classified by that rule.

## Study 3

Range `ab6135e11aeb` → `156dc93d940e`, `TaskComplexity` and its consumers.

**Matches**

- **Changed symbols.** 26 rows, the same split: 12 `uncertain`, 9
  `modified`, 4 `added`, 1 `signature_changed`
  (`input.rs#parse_task_complexity`). All twelve `uncertain` rows are the ones
  the explorer listed. Ten of them are provably unchanged symbols whose
  selector the index collapses, and they are still reported as `uncertain`,
  not as unchanged, and not dropped.
- **`parse_task_complexity` callers, complete and correct.**
  - `parse_assessed_task_complexity` at
    `crates/orbit-core/src/adapter/tool_host/input.rs:319@156dc93d`,
    `call_path` / `exact`, distance 1;
  - `task_tools.rs#add` at `task_tools.rs:62@156dc93d` → that call,
    `call_path` / `import_resolved`, distance 2.

  Ground truth (`git grep "parse_task_complexity("`) has exactly these, plus
  the `update` caller below.
- **Cross-crate consumers of `TaskComplexity`.** 59 distance-1 callers:
  - 3 `exact`, 55 `same_module`, 1 `import_resolved`;
  - from 35 files in `orbit-cli`, `orbit-config`, `orbit-core`, `orbit-store`,
    `orbit-types` and `orbit-web`.

  The explorer's ORB-12417 re-run counted 60 edges (4 exact, 55
  `same_module`, 1 `import_resolved`) from 32 files in the same six crates.
  Callers are distinct symbols and edges are not, and the command also counts
  base-side callers, which explains the small differences. At the default
  caps the 10 kept callers are the strongest (3 `exact`, 7 `same_module`),
  with `callers_found: 160` and a `max_callers` flag.
- **Import-relationship tests for `TaskComplexity`.** 140 were found, the
  same real-but-unrelated module-edge set the explorer described (136 then),
  all labelled `import_relationship` / `file_import`.

**New**

- **The caller the change rewired.** `task_tools.rs#update` is reported at
  distance 1 as calling `parse_task_complexity` at
  `crates/orbit-core/src/adapter/tool_host/task_tools.rs:336@ab6135e1`, the
  **base** side. Verified: at the base, line 336 is
  `.map(|value| parse_task_complexity("complexity", &value))`. At the head,
  the same line calls `parse_assessed_task_complexity`. The command analyses
  both sides of a modified or signature-changed symbol, so the call the change
  removed is shown with the commit it exists in. The explorer's Q4 read the
  head only and listed `update` at distance 2.
- **Non-fuzzy call-path tests.** At the fuzzy profile, 100 `call_path`
  test associations (summed over changed symbols) resolve at
  `import_resolved` (76) or `same_module` (24). The explorer
  reported "not one `call_path` candidate backed by a resolved call". The
  categories differ because this command labels each item with its path's
  weakest *confidence*, while the explorer counted *category* (every
  `same_module` hop is a `heuristic_match` category). The label an agent
  reads is now the one that distinguishes an import-resolved call from a
  name-only one.
- **Changed tests are their own entry points.** The three added tests are
  distance-0 entry points, labelled `changed_symbol` / `exact`.

**Missing, or different**

- **Two of the three added tests are candidates for `TaskComplexity`, not
  three.** The two found:
  - `crates/orbit-core/src/adapter/tool_host/tests/task_tools.rs` (imports
    `crate::application::task`);
  - `crates/orbit-web/src/api/tests/tasks.rs` (imports
    `orbit_core::application::task`).

  Both are `import_relationship` / `file_import`, among the 140. Missing:
  `crates/orbit-cli/src/command/task/tests/update.rs`. At
  `156dc93d` it imports only `crate::command::{Cli, Commands}` and
  `TaskSubcommand`, and it exercises complexity through clap parsing. No
  static edge links it to the type, so no source can find it. The explorer
  listed all three as present, and this run does not reproduce that for the
  CLI test. At the default caps (10 tests per symbol, ordered by source then
  path) neither found test is among the kept 10. `--symbol` with
  `--max-tests 500` shows them.
- **Plugin defaults leave one symbol unanalysed.** 26 changed symbols against
  the plugin's `max_symbols: 25`. One heading
  (`plugin/skills/orbit/references/task-authoring.md#Workflow`) is listed in
  `not_analysed` with reason `max_symbols`, and the cut is flagged.

## What this means for an agent

- **The labels carry the answer.** In both studies every item verified
  correct above is `exact`, `import_resolved` or `same_module`, with one
  exception: the teardown dispatcher, a genuine caller reachable only by
  name, which is labelled `fuzzy_name`. Every known false association is
  `fuzzy_name`, `file_import` or `name_only`. An agent that reads
  `confidence` before list position gets most of the explorer's manual
  verdicts without redoing the verification. `fuzzy_name` means "check the
  source", not "wrong".
- **Caps make the answer usable, and signal what they cut.** At defaults the
  plugin `result` was 264 KB (study 2) and 447 KB (study 3), and the CLI
  document 0.8–1 MB. The explorer produced 3–8 MB per study. Every
  cut is named in `truncation`, and `*_found` says how many were dropped.
- **The resolver limits are unchanged, and are no longer silent.** There is
  still no receiver-type inference for `.execute(&runtime)`, and there are no
  static edges from CLI-parsing tests. That is the explorer's
  [Limitations](../change-explorer/README.md), now visible on every row.
